# 4) Безопасность (Web/API)

## Authentication vs Authorization

**Authentication (аутентификация)** — установление личности. «Кто ты?» Проверка учётных данных (логин/пароль, токен, сертификат). Результат — identity (часто в виде `ClaimsPrincipal`).

**Authorization (авторизация)** — проверка прав. «Что тебе разрешено?» Проверка прав доступа к ресурсу (роль, claim, policy). Выполняется после аутентификации.

Порядок в pipeline: сначала Authentication middleware (заполняет `User`), затем Authorization (проверяет доступ к endpoint).

---

## Cookie vs JWT vs Opaque tokens

### Cookie-based

Токен (или session id) в cookie. HttpOnly — недоступен из JavaScript, защита от XSS. Secure — только HTTPS. SameSite — защита от CSRF. Подходит для браузерных SPA, когда backend и frontend на одном домене или настроен CORS.

### JWT (JSON Web Token)

Самодостаточный токен: payload + подпись. Сервер проверяет подпись, не хранит сессию. Stateless. Подходит для API, мобильных клиентов, микросервисов. Риски: хранение в localStorage — уязвим к XSS; нельзя отозвать до истечения срока (если не хранить blacklist). Короткий TTL + refresh token — типичная схема.

### Opaque tokens

Случайная строка, значение хранится на сервере. Проверка — lookup в БД/кэше. Можно отозвать в любой момент. Подходит, когда нужен жёсткий контроль и отзыв. Минус — состояние на сервере, нагрузка на хранилище.

### Выбор

- Браузер, один домен → Cookie.
- Stateless API, мобильные клиенты → JWT с коротким TTL.
- Необходим отзыв, централизованный контроль → Opaque.

## Policy-based authorization

Вместо проверки роли в коде — объявление политик в конфигурации. `AddAuthorizationBuilder()` или `AddAuthorization()` + `AddPolicy("PolicyName", policy => policy.RequireClaim("scope", "read").RequireRole("Admin"))`. На action: `[Authorize(Policy = "PolicyName")]`.

Политика может комбинировать требования: claim + role + custom `IAuthorizationHandler`. Удобно для сложных правил и переиспользования.

---

## Claims-based доступ

Идентификация и права выражены через claims (утверждения): `"sub"`, `"role"`, `"scope"`, кастомные. При авторизации проверяем наличие нужных claims. Проектирование: минимальный набор claims, необходимый для авторизации. Не хранить лишние персональные данные в токене. Проверка на каждом защищённом эндпоинте — не полагаться на то, что «где-то выше» уже проверили.

## Секреты и ротация

- **Хранение:** Azure Key Vault, HashiCorp Vault, переменные окружения. Не в коде, не в репозитории.
- **Ротация:** поддержка нескольких ключей (старый + новый). Постепенная смена: новые токены — новым ключом, старые ещё валидны. Без даунтайма.
- **Доступ:** минимальные права. Сервисные аккаунты с ограниченным доступом к секретам.

## Refresh token

Долгоживущий токен для получения новых access token. Хранить хэш (не сам токен). Связка с access token или session. Одноразовость: после использования — инвалидация. Expiration, привязка к устройству/клиенту (binding). При компрометации — отзыв refresh token, инвалидация сессии.

---

## Replay-атаки

Повторная отправка перехваченного запроса. Защита:
- **Nonce** — одноразовый идентификатор, сервер отклоняет повторы.
- **Timestamp** — отклонение запросов старше N секунд.
- **Подпись запроса** — включение timestamp/nonce в подпись, проверка на сервере.

Ограничение окна времени уменьшает окно для replay.

---

## CORS

Браузер ограничивает cross-origin запросы. CORS-заголовки (`Access-Control-Allow-Origin`, `Allow-Methods`, `Allow-Headers`) сообщают браузеру, какие запросы разрешены.

**Риски:** `*` в prod — любой сайт может делать запросы с учётными данными. Лишние методы/заголовки — расширение поверхности атаки. Настраивать только нужные origins, методы, заголовки. Preflight (OPTIONS) обрабатывать корректно.

---

## Mass assignment / Overposting

Клиент отправляет больше полей, чем ожидается. Модель биндинг привязывает их к entity. Злоумышленник добавляет `IsAdmin=true` — перезапись полей, которые не должны приходить извне.

**Защита:** использовать DTO с явным набором полей. `[BindNever]` для полей, которые не должны биндиться. Whitelist в `[Bind]`. Не биндить напрямую в entity из запроса.

---

## Hardening продового API

- **HTTPS only** — редирект HTTP → HTTPS, HSTS.
- **Заголовки безопасности** — `X-Content-Type-Options: nosniff`, `X-Frame-Options`, `Content-Security-Policy`, `Strict-Transport-Security`.
- **Rate limiting** — защита от brute-force, DoS.
- **Валидация входных данных** — размер, формат, санитизация.
- **Логирование без PII** — не логировать пароли, токены, персональные данные.
- **Минимальные права** — сервисные аккаунты, принцип наименьших привилегий.
- **Обновления** — патчи зависимостей, ОС, runtime.

---

## Best Practices

- **JWT** — короткий TTL (15–60 мин). Refresh token — отдельно, с rotation.
- **CORS** — не `*` в prod. Явный список origins.
- **Mass assignment** — всегда использовать DTO. Никогда не биндить напрямую в entity.
