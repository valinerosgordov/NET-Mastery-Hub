# 2) Асинхронность, многопоточность, конкурентность

## async/await под капотом

### State machine

Компилятор преобразует async-метод во вложенный struct (или class), реализующий `IAsyncStateMachine`. Каждый `await` — точка, где выполнение может приостановиться. Состояние (локальные переменные, позиция) сохраняется в полях state machine.

### Continuation

При `await` вызывается `GetAwaiter()`, получается `TaskAwaiter`. Если операция ещё не завершена, регистрируется continuation — колбэк, который будет вызван при завершении. Текущий поток освобождается. Continuation обычно выполняется на ThreadPool (если нет `SynchronizationContext`).

### Важно

`async` не создаёт новый поток. Это кооперативная многозадачность: поток отдаётся другим задачам, пока идёт I/O. При завершении I/O continuation ставится в очередь и выполняется (часто на том же или другом потоке из пула).

## Когда async ускоряет, а когда нет

### I/O-bound (сеть, диск, БД)

Поток блокируется на ожидании ответа. С `async` поток освобождается и может обрабатывать другие запросы. При 1000 одновременных запросах к БД:
- **Синхронно:** 1000 потоков (или очередь запросов).
- **Асинхронно:** десятки потоков, переключающихся между запросами.

Итог: выше throughput, меньше потребление памяти (потоки дороги).

### CPU-bound

Вычисления не освобождают поток — он занят. `async` сам по себе не даёт параллелизма. Нужно:
- `Task.Run(() => HeavyComputation())` — вынести на ThreadPool;
- `Parallel.ForEach` — для циклов;
- отдельные потоки.

### Смешанные сценарии

Комбинация: async для I/O, `Task.Run` для CPU-блоков внутри async-метода. Важно не оборачивать в `Task.Run` чистый I/O — это лишняя работа.

## async void

### Проблема

Исключения из `async void` не могут быть пойманы вызывающим. Они поднимаются в `SynchronizationContext` (например, в UI) и могут «ронять» приложение. Тестировать сложно — нет способа дождаться завершения.

### Исключение: обработчики событий

Сигнатура обработчика событий часто `void` (например, `button_Click`). Здесь `async void` допустим, но внутри нужен try-catch с логированием. Нельзя позволять исключению «улететь» наружу.

### Правило

Везде, где можно, — `async Task`. `async void` только для event handlers, и только с обработкой исключений внутри.

## Task vs ValueTask

### Task

- Класс, heap-аллокация при создании.
- Подходит для большинства сценариев.
- Можно многократно await-ить (но не рекомендуется).
- Кэширование: `Task.CompletedTask`, `Task.FromResult`.

### ValueTask

- Struct, обычно без heap-аллокации.
- Когда результат часто доступен синхронно (кэш hit, буфер в памяти) — можно вернуть `ValueTask.FromResult` без аллокации.
- Ограничение: await только один раз. Повторный await — undefined behavior.
- Используется в BCL: `ValueTask` для `Socket`, `Stream` и т.п.

### Выбор

- Публичный API, библиотеки — чаще `Task` (проще, предсказуемее).
- Hot path, внутренние методы с частым sync-путём — `ValueTask` для снижения аллокаций.

## Исключения в Task.WhenAll

### Поведение

При падении нескольких задач все исключения собираются в `AggregateException.InnerExceptions`. При `await Task.WhenAll(tasks)` пробрасывается первое исключение, остальные «теряются» для вызывающего (но есть в `InnerExceptions`).

### Обработка

```csharp
var tasks = new[] { Task.Run(() => Throw()), Task.Run(() => Throw()) };
try
{
    await Task.WhenAll(tasks);
}
catch (Exception ex)
{
    // ex — первое исключение
    // Все: проверить tasks, у failed — task.Exception.InnerExceptions
    foreach (var t in tasks.Where(t => t.IsFaulted))
        foreach (var inner in t.Exception!.InnerExceptions)
            Log(inner);
}
```

Альтернатива: `Task.WhenAll` не использовать для обработки, а обходить задачи и проверять `IsFaulted`, `Exception`.

## Deadlock с await

### Типичный сценарий

UI-поток (или любой с `SynchronizationContext`) вызывает синхронный код, который делает `SomeAsync().Result` или `Wait()`. Async-метод при продолжении пытается вернуться в тот же контекст. Но поток заблокирован на `Result`/`Wait` и не может обработать continuation. Взаимная блокировка.

### Решение

- Не использовать `.Result`/`.Wait()` на async-коде в контексте с `SynchronizationContext`.
- Пробрасывать async «наверх»: `async Task` до точки входа.
- В библиотеках: `ConfigureAwait(false)` — не захватывать контекст при продолжении (осторожно в UI).

## Sync-over-async

### Суть

Синхронный метод вызывает async через `.Result`/`.Wait()`. Поток блокируется в ожидании. При этом async-операция внутри может пытаться использовать ThreadPool для continuation. Результат: блокировка потока + возможное исчерпание пула (ThreadPool starvation).

### Опасность

В ASP.NET пул потоков ограничен. Много sync-over-async — потоки блокируются, новые запросы ждут. Latency растёт, возможен полный отказ.

### Правило

Не блокировать async. Если вызывающий синхронный — переписать на async или использовать sync-версию API, если она есть.

---

## ThreadPool starvation

### Причина

Слишком много потоков блокируются (sync-over-async, lock, длительный CPU) или слишком много задач в очереди. Пул не успевает обрабатывать новые запросы.

### Диагностика

- `ThreadPool.GetAvailableThreads(out var worker, out var io)` — сколько потоков свободно.
- Метрики: queue length, thread count.
- `dotnet-counters` — ThreadPool counters.
- Дамп потоков: `dotnet-dump` — смотреть, что делают потоки.

### Митигация

Устранить sync-over-async. Увеличить `SetMinThreads` (осторожно — больше потоков = больше памяти). Оптимизировать блокировки. Разнести CPU-bound нагрузку.

## CPU-bound vs I/O-bound

| Тип | Характеристика | Подход |
|-----|----------------|--------|
| **I/O-bound** | Ожидание диска, сети, БД | async/await, не держать потоки |
| **CPU-bound** | Вычисления, парсинг | `Task.Run`, `Parallel.*`, отдельные потоки |

I/O не требует потока во время ожидания. CPU требует активной работы потока. Смешивать не стоит: не оборачивать чистый I/O в `Task.Run`.

## CancellationToken

### Прокидывание

Передавать через все слои: контроллер → сервис → репозиторий → `HttpClient`, `DbContext` и т.д. Многие API принимают `CancellationToken`.

### Проверка

`ct.ThrowIfCancellationRequested()` — бросает `OperationCanceledException` при отмене. Или вручную: `if (ct.IsCancellationRequested) return;`.

### Игнорирование

Если не проверять и не передавать в API: операция продолжит выполняться после отмены запроса. Утечка ресурсов, лишняя нагрузка, пользователь уже ушёл. В ASP.NET при разрыве соединения `HttpContext.RequestAborted` отменяется — его нужно передавать вниз.

## Parallel.ForEach vs await foreach

### Parallel.ForEach

Для CPU-bound: параллельное выполнение на нескольких ядрах. Блокирует вызывающий поток до завершения. Подходит для обработки коллекций в памяти (расчёты, обработка изображений).

### await foreach

Для `IAsyncEnumerable<T>`: асинхронное перечисление. Поток не блокируется. Подходит для стриминга из БД (`EF Core` с `AsAsyncEnumerable`), из сети, из файлов. Один элемент за раз, без загрузки всего в память.

### Выбор

- Много CPU-работы над коллекцией → `Parallel.ForEach`.
- Асинхронный источник данных, стриминг → `await foreach`.

## Race condition

### Определение

Несколько потоков обращаются к общему состоянию, хотя бы один пишет, и результат зависит от порядка выполнения. Недетерминированное поведение, возможна порча данных.

### В проде

- Логи с correlation id, thread id.
- Трассировка запросов.
- Дампы при воспроизведении.
- Нагрузочное тестирование для провокации гонок.
- Статический анализ, code review на shared state.

## lock vs SemaphoreSlim vs Monitor vs Interlocked

| Примитив | Назначение | Когда использовать |
|----------|------------|-------------------|
| **lock** | Mutex для одного объекта | Простая эксклюзивная блокировка |
| **Monitor** | То же + `TryEnter`, `Wait`, `Pulse` | Условная блокировка, очереди |
| **SemaphoreSlim** | Счётчик, ограничение параллелизма | Не более N одновременных операций |
| **Interlocked** | Атомарные операции | Инкремент, compare-exchange, без lock |

**lock** — синтаксический сахар над `Monitor.Enter`/`Exit`. Для простых случаев достаточно.

**Interlocked** — для счётчиков, флагов. Быстрее lock, но только для примитивов.

**SemaphoreSlim** — например, ограничение до 10 одновременных HTTP-вызовов к внешнему API. `WaitAsync` для async-сценариев.

## ConcurrentDictionary

### Что даёт

Потокобезопасные `TryAdd`, `GetOrAdd`, `AddOrUpdate`, `TryGetValue`. Не нужен внешний lock для этих операций.

### Чего не даёт

Атомарность сложной бизнес-логики. Например: «прочитать, проверить условие, обновить» — между шагами другой поток может изменить данные. Нужен lock или `AddOrUpdate` с фабрикой.

### Пример

```csharp
// Атомарно
dict.AddOrUpdate(key, _ => 1, (_, count) => count + 1);

// НЕ атомарно — race между TryGetValue и indexer
if (!dict.TryGetValue(key, out var v)) dict[key] = 1;
else dict[key] = v + 1;
```

---

## Потокобезопасная коллекция vs атомарная бизнес-операция

**Потокобезопасная коллекция** — отдельные операции (Add, Remove, Get) атомарны. Два потока могут одновременно вызывать `Add` — оба успешно выполнятся.

**Атомарная бизнес-операция** — логика «если X, то сделать Y» должна выполняться как единое целое. Два потока не должны видеть промежуточное состояние. Требует lock, `Monitor`, семафора или иной координации поверх коллекции.

Пример: «списать со счёта, если баланс достаточен». Проверка и списание должны быть в одной критической секции.

---

## Best Practices

- **CancellationToken** — всегда передавать. В ASP.NET: `HttpContext.RequestAborted`.
- **ConfigureAwait(false)** — в библиотеках. В приложениях — по умолчанию сохранять контекст.
- **ValueTask** — только когда sync-путь частый. Не использовать как return type для публичных API без явной причины.
