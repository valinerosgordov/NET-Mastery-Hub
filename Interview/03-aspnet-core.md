# 3) ASP.NET Core (API, pipeline, DI)

## Request pipeline

### Устройство

Pipeline — цепочка компонентов (middleware). Каждый получает `HttpContext` и решает: вызвать `next()` (передать дальше) или завершить обработку (short-circuit). Запрос проходит «вниз» по цепочке до endpoint, ответ — «вверх» обратно.

### Схема

```
Request → M1 → M2 → M3 → Endpoint → M3 → M2 → M1 → Response
```

Middleware, вызвавший `next()`, ждёт завершения вложенной цепочки, затем может обработать ответ. Порядок регистрации в `Program.cs` определяет порядок выполнения.

### Типичный порядок

1. Exception handling (первым — ловит всё ниже)
2. HTTPS redirect
3. CORS
4. Static files
5. Routing
6. Authentication
7. Authorization
8. Endpoint (контроллеры, Minimal API)

---

## Порядок middleware

Порядок критичен: каждый middleware видит результат работы следующих. Exception handler должен быть первым — иначе исключения из последующих не будут пойманы. CORS — до auth, чтобы preflight-запросы обрабатывались без токена. Auth — до endpoint, чтобы к моменту вызова action пользователь был аутентифицирован.

---

## Middleware vs Filters (MVC)

### Middleware

Работает на уровне всего pipeline. Не знает о MVC, контроллерах, actions. Подходит для: логирование, обработка ошибок, CORS, compression, custom headers. Выполняется для каждого запроса (если не short-circuit).

### Filters

Привязаны к MVC pipeline. Выполняются в контексте выбора action и модели. Типы: Authorization, Resource, Action, Exception, Result. Могут получать контекст action (параметры, результат). Подходят для: валидация на уровне action, кастомная авторизация, форматирование ответа.

### Выбор

- Глобальная логика, не зависящая от MVC → Middleware.
- Логика, зависящая от action, модели, результата → Filter.

## Встроенный DI-контейнер

Реализует `IServiceProvider`. Регистрация: `builder.Services.AddSingleton<T>()`, `AddScoped<T>()`, `AddTransient<T>()`. Разрешение через конструктор (constructor injection).

### Ограничения

- Нет условной регистрации «из коробки» (по ключу, по имени).
- Нет декораторов (обёрток над сервисами) без ручной настройки.
- Один lifetime на регистрацию (нет разных lifetime для одного типа в разных контекстах).
- В .NET 8+ добавлены keyed services.

Для сложных сценариев — Autofac, Scrutor и т.п.

---

## Transient, Scoped, Singleton

| Lifetime | Создание | Область видимости |
|----------|----------|-------------------|
| **Transient** | Новый экземпляр при каждом `GetService` | Один запрос к контейнеру |
| **Scoped** | Один на scope (в ASP.NET — на HTTP-запрос) | В рамках scope |
| **Singleton** | Один на приложение | Глобально |

### Scoped в Singleton — антипаттерн

Singleton живёт вечно. Если он получает Scoped-сервис (например, `DbContext`) через конструктор, то захватывает один scope навсегда. DbContext не предназначен для такого использования: утечка, возможные ошибки при параллельных запросах. Решение: внедрять `IServiceScopeFactory` и создавать scope в методе, получать DbContext из scope.

---

## Keyed services (.NET 8+)

Регистрация с ключом: `services.AddKeyedSingleton<IStorage>("azure", ...)`. Разрешение: `[FromKeyedServices("azure")] IStorage storage`. Полезно, когда несколько реализаций одного интерфейса и выбор зависит от контекста (конфигурация, tenant, feature).

## Options pattern

### IOptions&lt;T&gt;

Singleton. Значение читается при первом обращении и кэшируется. Изменения в конфигурации (например, `appsettings.json`) не подхватываются без перезапуска.

### IOptionsSnapshot&lt;T&gt;

Scoped. При каждом запросе читается актуальная конфигурация. Подходит для сценариев, где конфиг может меняться (reload) и нужна свежесть в рамках запроса.

### IOptionsMonitor&lt;T&gt;

Singleton. Текущее значение + возможность подписаться на изменения (`OnChange`). Подходит для фоновых сервисов, которые должны реагировать на смену конфига без перезапуска.

---

## Типовые ошибки при регистрации сервисов

1. **DbContext в Singleton** — см. выше.
2. **Циклические зависимости** — A → B → C → A. Контейнер не сможет построить граф. Решение: рефакторинг, введение интерфейсов, lazy resolution.
3. **Регистрация конкретного типа вместо интерфейса** — усложняет тесты, моки.
4. **Неверный lifetime** — stateful-сервис как Singleton (общее состояние между запросами), stateless как Scoped (лишние создания).
5. **Множественная регистрация** — последняя «побеждает» при разрешении по типу. Для коллекций — все регистрации попадают в `IEnumerable<T>`.

## Версионирование API

### Подходы

- **URL path:** `/api/v1/users`, `/api/v2/users`.
- **Query:** `?version=1`.
- **Header:** `Api-Version: 1`.

### Практика

Не ломать контракты в рамках мажорной версии. Устаревшие эндпоинты помечать `[Obsolete]`, планировать deprecation. Документировать изменения. Тесты на обратную совместимость.

---

## Minimal APIs

Легковесный способ объявить эндпоинты без контроллеров: `app.MapGet("/users", () => ...)`. Удобно для простых CRUD, прототипов, внутренних API.

### Ограничения

- Нет встроенной модели фильтров как в MVC.
- Валидация, авторизация — вручную или через расширения.
- Сложная маршрутизация, модели — MVC может быть удобнее.
- Тестирование — через `WebApplicationFactory`, как и MVC.

---

## Глобальная обработка ошибок

`app.UseExceptionHandler("/error")` — при необработанном исключении запрос перенаправляется на указанный путь. Альтернатива: кастомный middleware с try-catch вокруг `next()`.

**ProblemDetails** (RFC 7807) — стандартный формат ответа об ошибке: `type`, `title`, `status`, `detail`, `instance`, расширяемые поля. В ASP.NET Core — `ProblemDetails` из `Microsoft.AspNetCore.Mvc`.

Логирование — в middleware или в фильтре исключений. Не логировать чувствительные данные. В проде — не раскрывать stack trace в ответе.

---

## Idempotency для POST

Клиент отправляет заголовок `Idempotency-Key: <uuid>`. Сервер:
1. Проверяет, есть ли сохранённый ответ для этого ключа.
2. Если да — возвращает его (200 или ранее сохранённый статус).
3. Если нет — выполняет операцию, сохраняет результат по ключу, возвращает ответ.

Ключ хранится ограниченное время (например, 24 часа). Защита от дублей при retry, таймаутах, сбоях сети.

## Correlation-id / request-id

Middleware в начале pipeline:
- Читает `X-Correlation-Id` / `X-Request-Id` из входящего запроса или генерирует новый (например, `Guid`).
- Кладёт в `HttpContext.Items["CorrelationId"]`.
- Добавляет в заголовки ответа.
- При логировании — в scope: `using (logger.BeginScope("CorrelationId={Id}", id))`.

Все логи в рамках запроса получают один и тот же ID. Упрощает поиск по трассировке в распределённых системах.

## Rate limiting

`Microsoft.AspNetCore.RateLimiting` (ASP.NET Core 7+). Политики: fixed window, sliding window, token bucket, concurrency. Применяется к endpoint или глобально. При превышении — 429 Too Many Requests.

Размещение: после auth (чтобы учитывать пользователя при необходимости), до бизнес-логики. Можно комбинировать: разный лимит для анонимов и аутентифицированных.

---

## Health checks

- **Liveness** — жив ли процесс. Простой эндпоинт, возвращающий 200. Kubernetes перезапускает pod при падении.
- **Readiness** — готов ли принимать трафик. Проверка БД, кэша, внешних сервисов. Kubernetes не направляет трафик на pod, пока readiness не OK.

`AddHealthChecks()` + `AddCheck<T>()` для кастомных проверок. `MapHealthChecks("/health")`. Раздельные пути: `/health/live`, `/health/ready`.

---

## Логирование HTTP без утечки персональных данных

- Не логировать тело запроса/ответа с PII (пароли, токены, персональные данные).
- Маскировать заголовки: `Authorization`, `Cookie`, `X-Api-Key`.
- Structured logging — не включать чувствительные поля в свойства.
- Фильтры логов — убирать или хэшировать PII перед отправкой в хранилище.
- В dev можно логировать больше, в prod — минимум.

---

## Best Practices

- **Scoped в Singleton** — использовать `IServiceScopeFactory` и создавать scope в методе, не в конструкторе.
- **Options** — IOptionsSnapshot для конфига, который может меняться (reload). IOptionsMonitor — для фоновых сервисов.
- **Minimal API** — для простых эндпоинтов. Для сложной валидации и фильтров — рассмотреть MVC.
