# 1) C# и основы платформы .NET

## Class vs Struct: память, копирование, производительность

### Суть различий

**Class** — ссылочный тип (reference type). Экземпляр создаётся в heap, переменная хранит ссылку (указатель) на объект. При присваивании `a = b` копируется только ссылка — обе переменные указывают на один объект. Время жизни управляется сборщиком мусора (GC).

**Struct** — значимый тип (value type). Значение хранится «по месту»: на стеке при локальной переменной или inline внутри родительского объекта (класса или другого struct). При присваивании и передаче в метод копируется весь экземпляр побайтово. GC не управляет самим значением (но может управлять объектом, в котором struct встроен).

### Производительность: когда что выбирать

| Критерий | Class | Struct |
|----------|-------|--------|
| Размер | Любой | Рекомендуется < 16–24 байт |
| Аллокации | Каждый `new` = heap | Нет heap при локальных/полях |
| Копирование | Только ссылка (8 байт) | Вся структура |
| Cache locality | Разбросаны по heap | Часто рядом в памяти |

**Практика:**
- Маленькие DTO, координаты, ключи — `struct` или `readonly struct`.
- Большие объекты (>32 байт), изменяемое состояние — `class`.
- Struct в `List<T>` — при каждом `Add` происходит копирование; для больших struct это может быть дорого.

### Пример

```csharp
// Class — две переменные указывают на один объект
var a = new PointClass { X = 1, Y = 2 };
var b = a;
b.X = 10;  // a.X тоже 10

// Struct — копия
var c = new PointStruct { X = 1, Y = 2 };
var d = c;
d.X = 10;  // c.X остаётся 1
```

## Boxing / Unboxing

### Что происходит

**Boxing** — когда value type нужно представить как `object`. CLR выделяет объект в heap, копирует значение внутрь, возвращает ссылку. Аллокация + копирование.

**Unboxing** — извлечение value type из «коробки». Копирование из heap обратно в стек/поле. Может вызвать `InvalidCastException`, если реальный тип в box не совпадает с целевым.

### Где «стреляет» по производительности

1. **Коллекции до generics:** `ArrayList.Add(42)` — каждый `int` боксится.
2. **Интерполяция строк:** `$"Value: {number}"` — при определённых условиях может боксить.
3. **Enum:** `Enum.GetValues()` возвращает массив `object[]`, каждый элемент — boxed.
4. **Рефлексия, dynamic** — частый boxing при работе с value types.
5. **Словари с value type ключами:** `Dictionary<object, T>` с `int` ключом — boxing при каждом lookup.

### Решения

- Generic коллекции: `List<int>`, `Dictionary<int, T>`.
- `Span<T>`, `Memory<T>` для работы с буферами без boxing.
- `IEquatable<T>` для struct — избегаем boxing при вызове `Equals`.
- `Enum.GetValues<T>()` (generic overload) вместо `GetValues()`.

## IEnumerable, ICollection, IReadOnlyCollection, IQueryable

### Иерархия и назначение

```
IEnumerable<T>           — только GetEnumerator(), отложенное выполнение
    ↑
IReadOnlyCollection<T>   — + Count, без модификации
    ↑
ICollection<T>           — + Add, Remove, Clear
```

**IEnumerable** — минимальный контракт для перечисления. Не гарантирует повторное перечисление. Не гарантирует Count (может материализовать всю последовательность). LINQ по умолчанию возвращает `IEnumerable<T>` — ленивое выполнение.

**ICollection** — мутабельная коллекция. Count — O(1) если реализовано правильно.

**IReadOnlyCollection** — только чтение, Count + перечисление. Подходит для возврата из API, когда не хотим позволять модификацию.

**IQueryable** — не коллекция в памяти. Представляет запрос к провайдеру (EF, OData). Дерево выражений компилируется в SQL/другой язык. Выполнение происходит при перечислении (например, при `ToList()`). Используется для запросов к БД — фильтрация, сортировка выполняются на стороне сервера.

### Важно

`IQueryable` реализует `IEnumerable`, но до перечисления запрос не выполняется. Вызов `.ToList()` на `IQueryable` материализует результат и выполняет запрос.

## yield return

### Как работает

Компилятор генерирует вложенный класс — state machine. При каждом вызове `MoveNext()` выполнение продолжается с точки последнего `yield return`. Элементы создаются лениво — только при перечислении.

### Ограничения

- **try-catch:** нельзя `yield return` внутри `try` с `catch` — компилятор не может гарантировать вызов `finally` при досрочном прерывании перечисления.
- **ref/out:** итератор сохраняет состояние между вызовами; `ref`/`out` параметры не могут быть сохранены в state machine.
- **finally:** код в `finally` выполняется при `Dispose` перечислителя (например, при выходе из `foreach`), но `yield return` в `finally` невозможен.

### Когда использовать

Стриминг больших данных без загрузки всего в память. Генерация бесконечных последовательностей. Кастомная логика перечисления.

## record class vs record struct

### Сравнение

| Аспект | record class | record struct |
|--------|--------------|---------------|
| Расположение | Heap | Stack / inline |
| Equality | Value-based (по полям) | Value-based |
| `with` выражение | Создаёт копию с изменением | Создаёт копию |
| Наследование | Поддерживается | Нет |
| Mutable по умолчанию | Да | Да (C# 10+ `readonly record struct`) |

### Выбор

- **record class:** DTO, API-модели, immutable-объекты с наследованием. Когда размер или семантика «объекта» важнее производительности.
- **record struct** / **readonly record struct:** небольшие value-объекты (ID, координаты, ключи) в hot path. Меньше аллокаций, лучше cache locality.

## == и Equals для reference/value type

### Reference type

- `==` по умолчанию сравнивает ссылки (если не перегружен).
- `Equals(object)` по умолчанию тоже сравнивает ссылки.
- Для `string` оба перегружены — сравнивается содержимое.

### Value type

- `==` и `Equals` по умолчанию — value equality (поле за полем).
- `Equals(object)` вызывает boxing — передаётся `object`, внутри unboxing. Для часто вызываемых struct это накладные расходы.

### Рекомендация для struct

Реализовать `IEquatable<T>` и переопределить `Equals(object)`:

```csharp
readonly struct Id : IEquatable<Id>
{
    public Guid Value { get; }
    public bool Equals(Id other) => Value == other.Value;
    public override bool Equals(object? obj) => obj is Id id && Equals(id);
    public override int GetHashCode() => Value.GetHashCode();
}
```

Так избегаем boxing при вызове `Equals(Id)`.

## GetHashCode

### Контракт

1. Если `Equals(a, b) == true`, то `GetHashCode(a) == GetHashCode(b)`.
2. Хеш должен быть стабильным в течение времени жизни объекта (пока объект в коллекции).
3. Идеально — равномерное распределение для разных значений.

### Зачем это важно

`Dictionary` и `HashSet` используют хеш для выбора бакета. При несогласованности с `Equals` возможны дубликаты в `HashSet` или потеря элементов в `Dictionary`. При плохом распределении хешей — деградация до O(n).

### Реализация

```csharp
public override int GetHashCode() => HashCode.Combine(Field1, Field2, Field3);
```

`HashCode.Combine` (NET Core 2.1+) даёт хорошее распределение. Для старых версий — комбинировать вручную (например, умножение на простое число и сложение).

## Nullable reference types

### Суть

При включённом `<Nullable>enable</Nullable>`:
- `string` — компилятор считает, что null не ожидается.
- `string?` — null допустим.
- Предупреждения при присвоении null в non-nullable, при разыменовании без проверки.

### Влияние на API

- Явный контракт: метод `GetName()` возвращает `string?` — вызывающий обязан обработать null.
- Меньше неожиданных `NullReferenceException`.
- Документация «в коде» — типы показывают намерение.

### Ограничения

Это только аннотации и предупреждения. В runtime проверок нет. Старый код и внешние библиотеки могут передавать null в non-nullable. `null!` подавляет предупреждение (использовать осторожно).

## ref, out, in

| Модификатор | Передача | Чтение | Запись | Типичное использование |
|-------------|----------|--------|--------|-------------------------|
| **ref** | По ссылке | Да | Да | Двусторонняя передача |
| **out** | По ссылке | До присвоения — нет | Обязательно | Возврат нескольких значений |
| **in** | По ссылке readonly | Да | Нет | Большие struct без копирования |

**in** — компилятор гарантирует, что метод не изменит значение. Позволяет передавать readonly ref для struct, избегая копирования. Полезно в hot path с большими struct.

---

## readonly struct

Все поля должны быть `readonly`. Компилятор может агрессивнее оптимизировать. Исключаются случайные мутации при копировании. Рекомендуется для небольших value-типов, которые по смыслу неизменяемы.

## Span&lt;T&gt; / Memory&lt;T&gt;

### Span&lt;T&gt;

- `ref struct` — может существовать только на стеке.
- Представляет непрерывный участок памяти (массив, stackalloc, unmanaged).
- Zero-allocation срезы: `span.Slice(1, 5)` не копирует данные.
- Не может быть полем класса, переходить через `await`, храниться в heap.

### Memory&lt;T&gt;

- Обычный struct — может быть полем, переходить через async.
- Представляет буфер, которым владеет кто-то другой.
- Для асинхронных API, когда нужно передать буфер между методами.

### Когда использовать

- Парсинг строк/байтов без `Substring`/копирования.
- Работа с буферами из `ArrayPool`.
- Hot path, где важна минимизация аллокаций.

---

## stackalloc

Выделение памяти на стеке. Синтаксис: `Span<int> buffer = stackalloc int[128];`. Память освобождается при выходе из метода. Без участия GC.

### Риски

- **Stack overflow:** стек ограничен (обычно 1 МБ по умолчанию). Большие `stackalloc` могут переполнить.
- **ref struct:** результат `stackalloc` — `Span<T>`, который нельзя сохранить в heap.

### Ограничения

- Размер должен быть известен на этапе компиляции или ограничен константой.
- Не использовать для больших буферов (предпочтительнее `ArrayPool`).

## Generic constraints

| Constraint | Допустимые типы |
|------------|-----------------|
| `where T : struct` | Только value types (включая nullable: `int?`) |
| `where T : class` | Только reference types |
| `where T : unmanaged` | Только примитивы и struct из примитивов (без ссылок) |
| `where T : new()` | Тип с публичным параметрless-конструктором |
| `where T : Base` | Наследники Base |
| `where T : IFace` | Реализующие IFace |

**unmanaged** строже **struct**: исключает `int?`, `struct` с полями-ссылками. Нужен для `Span<T>`, `stackalloc`, unsafe-кода, interop.

---

## ref struct

Ограничения из-за того, что не может пережить стековый фрейм:
- Не поле обычного класса.
- Не элемент массива.
- Не в `async` (state machine живёт в heap).
- Не в замыкании (closure может жить дольше).
- Не в `yield return` (итератор — класс в heap).

Используется для `Span<T>`, `ReadOnlySpan<T>`, `Stackalloc`-буферов — типов, которые должны быть привязаны к стеку.

## Ковариантность и контравариантность

### Ковариантность (out)

Более производный тип можно подставить вместо базового. `IEnumerable<Cat>` можно присвоить `IEnumerable<Animal>`, если `Cat : Animal`. Безопасно: мы только читаем, и каждый элемент — гарантированно `Animal`.

### Контравариантность (in)

Более базовый тип можно подставить вместо производного. `IComparer<Animal>` можно присвоить `IComparer<Cat>`. Безопасно: мы передаём в компаратор только `Cat`, а он умеет сравнивать любого `Animal`.

### Без in/out

`IEnumerable<T>` инвариантен без `out`. С `out T` становится ковариантным. `IComparer<T>` с `in T` — контравариантным. Это позволяет безопасно подставлять производные/базовые типы в обобщённых API.

## Best Practices

- **Struct vs class** — при сомнении выбирать class. Struct — только когда доказана польза (профилирование, hot path).
- **Span в API** — не возвращать `Span<T>` из публичных методов. Использовать `ReadOnlySpan<T>` для входных параметров.
- **GetHashCode** — при изменяемых полях в ключе: не использовать такие объекты в Dictionary/HashSet.
