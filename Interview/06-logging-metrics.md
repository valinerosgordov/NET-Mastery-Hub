# 6) Логирование, метрики, трассировка, диагностика

## Логи vs метрики vs трейсы

### Логи

События с контекстом. «Что произошло, когда, с какими данными». Текстовые или структурированные записи. Используются для отладки, расследования инцидентов, аудита. Не подходят для алертинга в реальном времени (задержка, объём).

### Метрики

Числовые показатели во времени. RPS, latency (p50, p95, p99), error rate, использование CPU/memory. Агрегируются, хранятся компактно. Используются для алертов, дашбордов, трендов. Prometheus, Grafana, Application Insights.

### Трейсы

Распределённая трассировка — путь запроса через сервисы. Каждый span — операция с длительностью. Позволяет видеть, где запрос провёл время, какие сервисы вызваны. Jaeger, Zipkin, OpenTelemetry.

### Комбинирование

Логи — детали при инциденте. Метрики — алерты и тренды. Трейсы — сквозной анализ latency. Correlation ID связывает логи и трейсы в рамках одного запроса.

---

## Structured logging

Вместо строки `"User 123 logged in"` — структурированные поля: `{ "UserId": 123, "Event": "Login" }`. В JSON или key-value формате. Системы (ELK, Loki, Splunk) индексируют поля, позволяют фильтровать и агрегировать. Поиск «все логи для UserId=123» — без regex по тексту.

В .NET — `ILogger` с параметрами: `logger.LogInformation("User {UserId} logged in", userId)`. Параметры попадают в структурированные поля.

---

## Уровни по окружениям

| Окружение | Уровень по умолчанию | Комментарий |
|-----------|---------------------|-------------|
| **Dev** | Debug | Максимум деталей для отладки |
| **Stage** | Information | Близко к prod, но можно больше |
| **Prod** | Warning | Минимум шума. Information для бизнес-событий (оплата, регистрация) |

В prod не логировать Debug/Trace в обычном режиме — объём и стоимость. При инциденте временно повысить детализацию.

---

## Log noise vs сигнал

**Шум** — избыточные логи, дублирование, нерелевантная информация. Затрудняет поиск важного.

**Сигнал** — релевантные события, контекст, возможность быстро найти причину.

**Приёмы:** фильтрация по уровню; не логировать в горячем цикле; группировка (один лог на batch вместо N); sampling для высоконагруженных путей; correlation id для связки; структурированные поля для фильтрации.

---

## Observability для микросервиса

Три столпа: логи, метрики, трейсы. Плюс:
- Correlation ID — сквозной идентификатор запроса.
- Экспорт в общую систему: Prometheus, Grafana, Jaeger, OpenTelemetry.
- Health checks — liveness, readiness.
- Стандартизация форматов и атрибутов для кросс-сервисного анализа.

| Утилита | Назначение |
|---------|------------|

## Утечки памяти в managed-коде

1. **Создать дамп** — `dotnet-dump collect` или `dotnet-gcdump`.
2. **Анализ heap** — какие объекты занимают память, кто их удерживает (roots).
3. **Сравнение дампов** — до и после нагрузки. Какие типы растут.
4. **Поиск причин** — статические поля, кэши без ограничения, подписки на события, незакрытые ресурсы.

Типичные причины: кэш без eviction, хранение в статике, захват в замыканиях, не отписанные event handlers.

## Spike latency без явных ошибок

Запросы медленные, но без исключений. Подход:
- Метрики p95/p99 — где рост.
- Трейсы — в каком сервисе/операции задержка.
- Профилирование CPU — что занимает время.
- Проверка GC — паузы, gen2 collections.
- ThreadPool — starvation, очередь.
- Внешние зависимости — БД, HTTP, диски.

---

## Рост p95/p99 — что проверить

1. **Внешние вызовы** — сеть, БД, сторонние API. Latency, таймауты.
2. **GC** — паузы, частота сборок, размер heap.
3. **Lock contention** — потоки ждут lock.
4. **ThreadPool starvation** — очередь задач, блокирующие вызовы.
5. **БД** — N+1, отсутствие индексов, медленные запросы, connection pool.
6. **Сериализация** — большие объекты, неэффективные сериализаторы.

## Alert fatigue

Слишком много алертов, много ложных срабатываний — команда перестаёт реагировать. Решения:
- Пороги по SLO — алерт только при нарушении целевых метрик.
- Агрегация — один алерт на группу проблем.
- Severity — разделение критичного и информационного.
- Избегать дублирования — один инцидент = один алерт.
- Runbooks — что делать при срабатывании.
- Регулярный пересмотр — отключать нерелевантные, настраивать пороги.

---

## Best Practices

- **Structured logging** — ключ-значение, не интерполяция в строку. `LogInformation("Order {OrderId} created", orderId)`.
- **Correlation ID** — в каждом логе. Без него невозможно связать события одного запроса.
- **Уровни** — Debug только в dev. Prod: Warning по умолчанию, Information для бизнес-событий.
