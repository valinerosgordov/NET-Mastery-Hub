# 5) EF Core, SQL, доступ к данным

## Change tracker

### Назначение

Отслеживает сущности, загруженные через контекст. Реализует Identity Map — один экземпляр сущности на ключ. При `SaveChanges` выполняет dirty checking — сравнивает текущее состояние с исходным и генерирует INSERT/UPDATE/DELETE.

### Влияние на память и производительность

Для каждой отслеживаемой сущности хранится: ссылка на объект, оригинальные значения, состояние (Added, Modified, Deleted, Unchanged). При большом количестве сущностей — значительное потребление памяти и накладные расходы при `SaveChanges`.

### Когда отключать

Для read-only сценариев — `AsNoTracking()`. Запросы только на чтение не требуют отслеживания. Экономия памяти и ускорение.

```csharp
// Read-only — без tracking
var orders = await context.Orders
    .AsNoTracking()
    .Where(o => o.Status == OrderStatus.Active)
    .Select(o => new OrderDto(o.Id, o.Total, o.Customer.Name))
    .ToListAsync(ct);

// Глобально для контекста
protected override void OnConfiguring(DbContextOptionsBuilder options)
    => options.UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking);
```

---

## Tracking vs AsNoTracking

| Режим | Использование | Память | Скорость |
|-------|---------------|--------|----------|
| **Tracking** | Изменения, lazy loading, identity map | Выше | Ниже |
| **AsNoTracking** | Только чтение | Ниже | Выше |

**Tracking** нужен для: `Update`, `Remove`, lazy loading навигаций. Для выборок, которые только отображаются или возвращаются в API, — `AsNoTracking`.

## Include и Cartesian explosion

### Проблема

При нескольких `Include` с коллекциями EF генерирует один SQL с JOIN. Например, Order с OrderItems и OrderShipments. Каждая строка Order умножается на количество OrderItems и OrderShipments. Декартово произведение — дублирование данных, раздувание результата.

### Решение: AsSplitQuery()

Вместо одного запроса — несколько: один для Order, один для OrderItems, один для OrderShipments. EF объединяет результаты в памяти. Нет explosion, но больше round-trips к БД. Настройка: `AsSplitQuery()` в цепочке запроса или глобально в конфигурации контекста.

### Когда применять

- Несколько коллекций в Include → рассмотреть `AsSplitQuery`.
- Одна коллекция, небольшой объём — single query может быть эффективнее (меньше round-trips).

---

## AsSplitQuery vs single query

**Single query** — один SQL, один round-trip. При нескольких коллекциях — Cartesian explosion, большой объём данных по сети.

**AsSplitQuery** — N запросов, N round-trips. Нет explosion. При медленной сети или большом количестве коллекций часто выгоднее.

## N+1

### Суть

Один запрос загружает список сущностей (например, Orders). При обращении к навигации (Order.Customer) для каждой строки выполняется отдельный запрос. 1 + N запросов.

### Решения

1. **Include** — явная загрузка связи в первом запросе.
2. **Проекция в DTO** — `Select(o => new OrderDto { ..., CustomerName = o.Customer.Name })` — один запрос с JOIN.
3. **Явная загрузка** — `context.Entry(order).Reference(o => o.Customer).Load()` — когда нужна ленивая загрузка по требованию.

Проекция в DTO часто лучше — загружаем только нужные поля, без лишних данных.

---

## Оптимизация LINQ

- **Проекция** — `.Select()` в DTO на стороне БД. Не загружать entity целиком, если нужны только поля.
- **Фильтрация до Include** — `Where` перед `Include`, чтобы не тянуть лишние связи.
- **AsNoTracking** для reads.
- **Избегать client-side evaluation** — операции, которые EF не может перевести в SQL (например, вызов методов в `Where`), выполняются в памяти. Проверять логи EF на предупреждения.
- **Пагинация** — `Skip`/`Take` или keyset на стороне БД.

---

## Compiled queries

`EF.CompileQuery()` компилирует дерево выражений один раз. Повторные вызовы используют скомпилированный план. Экономия на парсинге и компиляции. Эффект при частом выполнении одного и того же запроса с разными параметрами.

Ограничение: параметры должны быть примитивами или простыми типами. Сложные объекты не поддерживаются.

---

## Query caching

EF кэширует скомпилированные запросы (compiled model, query plan). Повторные вызовы с теми же структурой и параметрами используют кэш. Не путать с кэшированием результатов — только план запроса.

---

## Optimistic concurrency

Предполагаем, что конфликты редки. При `SaveChanges` проверяем, не изменилась ли строка с момента чтения. Реализация: колонка `RowVersion` (timestamp) или `[ConcurrencyCheck]` на полях. В UPDATE добавляется `WHERE RowVersion = @oldVersion`. Если 0 строк затронуто — `DbUpdateConcurrencyException`. Обработка: перезагрузить сущность, повторить или показать пользователю конфликт.

---

## Транзакции при нескольких SaveChanges

Одна бизнес-операция — несколько вызовов `SaveChanges` (например, разные агрегаты). Нужна одна транзакция:

```csharp
await using var transaction = await context.Database.BeginTransactionAsync();
try
{
    // ... операции, SaveChanges
    await transaction.CommitAsync();
}
catch { await transaction.RollbackAsync(); throw; }
```

Для нескольких контекстов — `TransactionScope` или общая connection, переданная в оба контекста.

---

## Raw SQL (FromSql/ExecuteSql)

**FromSqlRaw** — для запросов с возвратом сущностей. Параметры — только через плейсхолдеры (`{0}`, `{1}`) или `FromSqlInterpolated`. Никогда не конкатенировать строки — SQL-инъекции.

**ExecuteSqlRaw** — для INSERT/UPDATE/DELETE без загрузки сущностей.

Когда использовать: сложные запросы, которые LINQ не выражает; производительность; специфичные возможности SQL.

---

## Пагинация без деградации

**OFFSET/FETCH** — на больших offset (например, страница 10000) БД всё равно сканирует и пропускает строки. Деградация при росте offset.

**Keyset (cursor) пагинация** — `WHERE id > @lastId ORDER BY id LIMIT @pageSize`. Стабильная производительность. Ограничение: нельзя «прыгнуть» на произвольную страницу, только вперёд/назад от курсора.

---

## Индексы под запросы

Анализ планов выполнения (EXPLAIN, Query Plan). Индексы на колонки в WHERE, JOIN, ORDER BY. Composite index для частых комбинаций (например, `(TenantId, CreatedAt)`). Покрывающие индексы (include columns) для запросов, которые читают только часть колонок.

---

## Query tags

`TagWith("GetOrdersByCustomer")` — добавляет комментарий в SQL. В логах и профилировщике видно, какой код сгенерировал запрос. Упрощает поиск медленных запросов.

## Диагностика EF

- Логирование SQL — `LogTo` или ILogger.
- Метрики — `DiagnosticListener`, события EF.
- Профилирование — SQL Profiler, Application Insights.
- `EnableSensitiveDataLogging` — только в dev, логирует значения параметров.

---

## Репозиторий поверх EF

**За** — абстракция источника данных, смена EF на Dapper/сырой SQL без изменения домена; тестируемость (мок репозитория).

**Против** — часто это тонкая обёртка над `DbSet`, не добавляющая ценности. EF уже абстрагирует БД. Дублирование возможностей EF (например, `IQueryable` в репозитории — утечка абстракции).

**Когда уместен** — при реальной смене источника, сложной доменной логике доступа к данным, агрегатах с инкапсулированными запросами.

---

## Fan-out запросов к БД

Много запросов в цикле или параллельно — нагрузка на БД. Решения: batch-запросы (одним запросом загрузить нужные данные), кэширование, денормализация. Избегать N запросов в цикле — заменить на один с фильтром по списку ID.

---

## Миграции при конкурентных деплоях

Несколько инстансов деплоятся одновременно. Миграции должны применяться один раз. Варианты:
- Миграции — отдельный шаг до деплоя приложения (отдельный job в CI/CD).
- Leader/lock — только один инстанс применяет миграции (например, через distributed lock).
- Идемпотентные миграции — проверка существования перед применением.

---

## Best Practices

- **AsNoTracking по умолчанию** — для read-only API. Только для изменений включать tracking.
- **Проекция** — `.Select()` в DTO до `ToListAsync()`. Не загружать entity целиком, если нужны 2–3 поля.
- **TagWith** — для каждого сложного запроса. Упрощает поиск в логах.
