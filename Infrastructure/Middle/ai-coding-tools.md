# AI-инструменты разработчика 2026

> Ландшафт AI-tooling глазами .NET-разработчика: от автодополнения до автономных агентов в CI. Кто есть кто (GitHub Copilot, Claude Code, Cursor, JetBrains AI), как строить агентный workflow, что AI умеет в code review — и какая дисциплина нужна, чтобы всё это не превратилось в фабрику технического долга.

## 1. Ландшафт 2026

### 1.1. Четыре поколения инструментов

Рынок прошёл четыре ступени, и каждая следующая **не отменяет** предыдущую — они сосуществуют в одном рабочем дне:

| Поколение | Что делает | Примеры | Кто контролирует результат |
|-----------|-----------|---------|---------------------------|
| **Автодополнение** | Продолжает строку/блок по контексту файла | Copilot completions, JetBrains full-line completion | Ты — принимаешь Tab'ом каждую подсказку |
| **Чат** | Отвечает на вопросы, объясняет, генерирует сниппеты | Copilot Chat, AI Assistant chat | Ты — копируешь то, что счёл верным |
| **Агент в IDE** | Многофайловые правки: сам читает проект, редактирует, запускает build/тесты, итерирует по ошибкам | Copilot agent mode, Claude Code, Cursor Composer, JetBrains Junie | Ты — ревьюишь diff перед принятием |
| **Агент в CI/фоне** | Работает асинхронно вне IDE: получает issue — возвращает PR | Copilot coding agent, Cursor cloud agents, Claude Code в headless/CI-режиме | Ты — ревьюишь PR как от чужого джуна |

Ключевой сдвиг 2025–2026: центр тяжести ушёл от «подсказка в строке» к **агентному циклу** — инструмент сам планирует, правит и проверяет себя компилятором и тестами. Чем ниже по таблице, тем больше leverage и тем дороже цена невнимательного ревью.

### 1.2. Основные игроки

**GitHub Copilot** — дефолт корпоративного мира.
- ✅ Нативная интеграция с GitHub: agent mode в VS Code/JetBrains/Visual Studio, coding agent (назначил issue → получил PR через GitHub Actions), code review из коробки, кастомные агенты со своими инструкциями и MCP-серверами.
- ✅ Проще всего «продать» в enterprise: биллинг, комплаенс и данные уже у Microsoft.
- ❌ Jack of all trades: в глубоких агентных сессиях уступает специализированным инструментам; качество сильно зависит от выбранной модели под капотом.

**Claude Code** — терминальный агент Anthropic.
- ✅ Сильнейший «глубокий» агент: длинные многошаговые задачи, работа через CLI без привязки к IDE, скриптуется в CI. По данным JetBrains-исследования (январь 2026) — самая высокая лояльность на рынке (CSAT 91%, NPS 54) при adoption ~18% (в США/Канаде до 24%).
- ✅ Первоклассная поддержка MCP и контекст-файлов (CLAUDE.md).
- ❌ Терминальный UX — порог входа для тех, кто живёт в IDE; стоимость длинных сессий заметна.

**Cursor** — AI-first форк VS Code.
- ✅ Самый отточенный in-IDE агентный UX: Composer, параллельные фоновые агенты в облачных VM, мгновенное «tab-tab-tab» редактирование. Многомиллиардная оценка компании — индикатор темпа, не качества, но команда шипит фичи быстрее всех.
- ❌ Отдельный редактор: экосистема Visual Studio/Rider (профилировщики, дизайнеры, XAML tooling) остаётся за бортом — для .NET это ощутимо.
- ❌ Vendor lock-in на редактор и подписку.

**JetBrains AI (AI Assistant + агент Junie)** — ставка на глубину IDE.
- ✅ Единственный игрок, у которого AI опирается на **семантическую модель кода** (индексы, типы, usages), а не только на текст файлов — для C#/Rider это даёт точные правки и рефакторинги.
- ✅ Junie показывает конкурентные результаты на агентных бенчмарках; локальные модели поддерживаются.
- ❌ Позже всех вышли на агентный рынок; квоты/кредиты вызывают больше всего жалоб пользователей.

### 1.3. Adoption: цифры среза (дрейфуют)

- **Stack Overflow Developer Survey 2025** (опубликован в июле 2025): 84% разработчиков используют или планируют использовать AI-инструменты (было 76% годом ранее); 51% профессионалов — ежедневно.
- **Парадокс доверия**: лишь 29% доверяют точности AI-вывода (было 40% в 2024), 46% активно **не** доверяют, и только 3% «доверяют полностью». Использование растёт — доверие падает. Это здоровая динамика: рынок научился видеть галлюцинации.
- **Агенты отстают от хайпа**: половина разработчиков агентами не пользуется вовсе или ограничивается простыми инструментами.
- **JetBrains State of Developer Ecosystem 2025** (опубликовано в октябре 2025): 85% регулярно применяют AI в работе, 62% используют хотя бы один AI-ассистент/агент/редактор.

### 1.4. Почему .NET — хорошая среда для агентов

Агентный цикл живёт обратной связью: правка → сборка → тесты → следующая итерация. Строгая типизация и компилятор дают агенту **дешёвый и быстрый сигнал об ошибке** — `dotnet build` ловит то, что в динамических языках всплывёт только в рантайме. Roslyn-анализаторы, `.editorconfig` и nullable reference types работают как автоматические рельсы: агент физически не может «проехать» мимо warning-as-error. Вывод: чем жёстче настроен твой build, тем полезнее агент — инвестиции в аналайзеры окупаются двойне.

## 2. Агентный workflow

### 2.1. Цикл: план → правки → тесты

Продуктивная работа с агентом — это не «напиши мне фичу», а управляемый цикл:

1. **План.** Просишь агента сначала изложить план (какие файлы, какие изменения, какие тесты). Читаешь. Правишь план — это в разы дешевле, чем править код.
2. **Правки.** Агент вносит изменения ограниченным скоупом. Хороший тон — один PR = одна задача, как и у людей.
3. **Тесты.** Агент запускает `dotnet build` и `dotnet test`, сам читает ошибки и итерирует. Твоя задача — убедиться, что тесты **содержательные** (см. 4.3), иначе цикл сойдётся к зелёному, но бессмысленному состоянию.
4. **Ревью.** Diff читается целиком, как чужой PR. Принял не читая — принял ответственность за то, чего не видел.

Правило масштаба: агенту — задачи, у которых есть **проверяемый критерий готовности** (компилируется, тесты зелёные, бенчмарк не просел). Задачи без критерия («сделай красиво») — источник бесконечных итераций.

### 2.2. Контекст-менеджмент: CLAUDE.md, AGENTS.md, rules

Агент не знает твоих конвенций, пока ты их не записал. Все инструменты сошлись на одном паттерне — **markdown-файл с инструкциями в корне репозитория**, который автоматически подхватывается в контекст:

| Файл | Кто читает |
|------|-----------|
| `AGENTS.md` | Кросс-инструментальный стандарт (agents.md): OpenAI Codex, Cursor, VS Code и десятки других |
| `CLAUDE.md` | Claude Code |
| `.cursor/rules/` | Cursor (модульные правила с glob-скоупами) |
| `.github/copilot-instructions.md` | GitHub Copilot |

Вложенность работает по принципу *nearest file wins*: файл в подпапке уточняет корневой — конвенции модуля живут рядом с кодом модуля.

**Что писать** (проверено практикой):
- Команды: как собрать, как запустить тесты, как поднять локально.
- Архитектурные инварианты: «Domain не ссылается на Infrastructure», «Result pattern вместо исключений», «sealed by default».
- Запреты: чего не делать никогда (менять миграции задним числом, коммитить в main, добавлять пакеты без согласования).

**Чего не писать**: пересказ README, историю проекта, всё «на всякий случай». Контекст-файл на 2000 строк агент прочитает — и утопит в нём важное. Работает то же правило, что и для людей: короткий актуальный документ лучше длинного мёртвого.

### 2.3. MCP — стандартный разъём для инструментов

**Model Context Protocol** — открытый протокол подключения внешних инструментов и данных к AI-агентам: базы, тикет-трекеры, внутренние API становятся вызываемыми функциями. Создан Anthropic (ноябрь 2024), в декабре 2025 передан в нейтральное управление под эгидой Linux Foundation; поддержан OpenAI, Google, Microsoft — фактически «USB-C для агентов», единственный выживший стандарт в своей нише.

Для .NET-разработчика это значит: один MCP-сервер на C# — и твой внутренний инструмент доступен из Claude Code, Copilot, Cursor и VS Code одновременно. Как писать MCP-серверы на C# (официальный SDK `ModelContextProtocol`, атрибуты, транспорты) — canonical deep-dive в [[mcp-csharp]].

Дисциплина: каждый подключённый MCP-сервер — это **расширение attack surface** агента. Сервер с правом писать в прод-базу превращает галлюцинацию в инцидент. Подключай минимум, разделяй read-only и мутирующие инструменты.

### 2.4. Фоновые агенты: issue in — PR out

Асинхронный режим (Copilot coding agent, облачные агенты Cursor, Claude Code в CI) меняет экономику мелких задач: типовой bugfix, добавление логирования, миграция API-вызовов — назначил и вернулся к своей работе. Хорошо ложится на задачи, где критерий готовности формален и покрыт тестами.

Обратная сторона: **ревью становится бутылочным горлышком**. Агент генерирует PR быстрее, чем человек их читает. Если команда не договорилась о лимитах (сколько агентных PR в день, кто владелец), очередь ревью растёт, а качество чтения падает — и весь выигрыш съедается.

## 3. AI в CI и code review

### 3.1. AI-ревьюеры

Класс инструментов, комментирующих PR автоматически: **Copilot code review** (встроен в GitHub, с 2026 умеет передавать свои замечания coding agent'у для автофикса), **CodeRabbit** (лидер по adoption: построчный разбор, саммари PR, диаграммы, обучение на фидбеке команды, работает и с GitLab), **Greptile**, **Qodo** и другие. В феврале 2026 появился первый независимый бенчмарк AI-ревьюеров (Martian) — до этого все цифры были вендорскими.

Что они реально умеют:

| Хорошо ловят | Слепые зоны |
|--------------|-------------|
| Null-ошибки, off-by-one, опечатки в логике | Архитектурные решения и их долгосрочная цена |
| Несоответствие стайлгайду, забытый dispose | Доменные инварианты («скидка не может превышать 100%») |
| Саммари PR — экономит время входа в контекст | Публичные контракты: правильно ли **менять** API вообще |
| Пропущенные edge cases в очевидных местах | «Код корректен, но решает не ту задачу» |

### 3.2. Гейтинг: AI-предложение ≠ merge

Принцип, который стоит закрепить в branch protection, а не в устных договорённостях:

- **AI-ревьюер — pre-filter, не судья.** Он снимает с человека механику (стиль, очевидные баги), чтобы человек читал то, что машина не видит: контракты, архитектуру, домен.
- **Человек владеет контрактами.** Изменения публичных API, схемы БД, миграций, security-чувствительного кода — требуют approve живого владельца. Required reviewers в GitHub настраиваются так, что approve AI-бота **не** удовлетворяет правило.
- **Автофикс от AI-ревьюера — это новый PR-цикл**, а не тихий коммит поверх. Иначе получается петля «AI ревьюит AI» без человека в контуре.

Куда встраивать в pipeline: AI-ревью — параллельно с build/test джобами, до человеческого ревью; результат — комментарии, не блокирующий гейт (блокируют — компилятор, тесты и человек). Настройка CI — в [[cicd-github-actions]].

## 4. Риски и дисциплина

### 4.1. Slopsquatting — галлюцинированные пакеты

Механизм: LLM уверенно советует пакет, которого **не существует** — правдоподобное имя, собранное из паттернов реальных названий. Атакующий заранее регистрирует такие имена в реестре и кладёт туда malware. Исследования 2025–2026: ~20% рекомендованных пакетов в выборке из 576 тыс. сгенерированных примеров были галлюцинациями (коммерческие модели — около 5%, open-source — свыше 20%); хуже того, разные модели галлюцинируют **одни и те же имена**, что делает атаку прицельной. В npm уже зафиксированы реальные вредоносные пакеты под галлюцинированными именами с тысячами скачиваний.

Дисциплина (для NuGet ровно та же, что для npm):
1. Перед `dotnet add package` — проверить существование пакета и **verified publisher / prefix reservation** на nuget.org.
2. Lock-файлы (`packages.lock.json`, `RestorePackagesWithLockFile`) + `--locked-mode` в CI: агент не может втащить новую зависимость незаметно.
3. Агенту в контекст-файл — явный запрет добавлять зависимости без согласования.

### 4.2. Лицензионная чистота сгенерированного кода

LLM обучены на открытом коде, включая GPL/AGPL. Генерация может **дословно воспроизвести** обученный фрагмент — и в проприетарный код въезжает копилефт-обязательство. Вероятность растёт для «известных» алгоритмов и узнаваемых утилит.

Практика: включать фильтры совпадений с публичным кодом (у Copilot — «suggestions matching public code: blocked»; enterprise-планы крупных вендоров дают IP indemnity); для больших сгенерированных кусков — прогон через сканер (ScanCode и аналоги) в том же ряду, что и license-аудит зависимостей. Юридически ответственность за то, что в репозитории, несёт автор коммита — «это AI написал» не аргумент.

### 4.3. Vacuous AI-тесты

Агент, которому сказали «подними покрытие», сгенерирует тесты, которые **исполняют** код, но почти ничего не **проверяют**: assert на то, что метод не бросил исключение, моки, зеркалящие реализацию, проверки конструктора. Coverage растёт, защита от регрессий — нет. Механизм: покрытие измеряет исполнение строк, а не силу утверждений, и оптимизирующий метрику агент честно эксплуатирует эту дыру (Goodhart's law в чистом виде).

Вскрывается mutation testing'ом: Stryker.NET мутирует код и смотрит, падают ли тесты — vacuous-тесты пропускают мутантов, и mutation score показывает реальную цену «зелёного» покрытия. Подробно — [[testing]]. Правило: AI-тесты проходят то же ревью, что и AI-код, а mutation score — периодический аудит их честности.

### 4.4. Секреты в промптах и контексте

Всё, что попадает в контекст агента, уходит на сервер вендора: connection strings в `appsettings.Development.json`, токены в `.env`, дампы прод-данных в отладочных файлах. Отдельный риск — MCP-серверы: инструмент с доступом к секрет-хранилищу может вернуть секрет в контекст, откуда тот утечёт в лог или в следующий запрос (exfiltration через prompt injection — уже задокументированный класс атак).

Дисциплина:
- Секреты — в user secrets / vault, **никогда** в файлах репозитория (это правило старше AI, агенты лишь повысили цену нарушения).
- Ignore-настройки инструментов: исключить `.env`, ключи, дампы из индексации и контекста.
- Secret scanning (GitHub push protection, gitleaks) в CI — ловит и человеческие, и агентные коммиты.
- Для enterprise: планы с zero data retention / без обучения на твоём коде — вопрос в чек-лист выбора вендора.

## 5. Common Pitfalls

1. **Принимать diff не читая.** Механизм: доверие калибруется по первым удачным задачам, потом наступает автопилот — а агент ошибается неравномерно: 10 тривиальных задач идеально, 11-я тихо ломает инвариант. Ревью — константа, не фаза онбординга.
2. **Один мегапромпт вместо цикла.** «Сделай всю фичу» → агент принимает десятки микрорешений без твоего участия, и переделка дороже, чем работа руками. Итерации: план → скоуп → ревью.
3. **Контекст-файл на 2000 строк.** Важные запреты тонут в пересказе README; агент «читал, но не усвоил» — ровно как человек. Короткий живой документ.
4. **Агент на legacy без тестов.** Циклу нечем себя проверять: build проходит, поведение молча меняется. Сначала characterization-тесты (см. [[testing]]), потом агент.
5. **AI-ревьюер как единственный ревьюер.** Слепые зоны (архитектура, домен, контракты) — систематические, они не устраняются «моделью получше». Pre-filter, не замена.
6. **Установка пакета из подсказки без проверки.** Slopsquatting (4.1): имя правдоподобное, пакет вредоносный. Проверка существования + publisher — всегда.
7. **KPI «процент кода от AI».** Метрика провоцирует принимать всё подряд и генерировать многословный код. Мерить нужно то же, что всегда: lead time, дефекты, mutation score.

### 5.1. Decision tree: агенту или руками

```
Задача имеет формальный критерий готовности (тесты/компиляция/бенчмарк)?
├─ НЕТ → руками (или сначала сформулируй критерий)
└─ ДА → Код покрыт тестами в зоне изменений?
    ├─ НЕТ → руками написать тесты (или агентом + жёсткое ревью тестов),
    │        потом агент для основной задачи
    └─ ДА → Задача трогает публичные контракты / миграции / security?
        ├─ ДА → агент под присмотром: план утверждаешь ты,
        │       ревью построчное, человек-владелец обязателен
        └─ НЕТ → Задача типовая и повторяющаяся (рефакторинг, миграция API,
                 boilerplate, тестовые данные)?
            ├─ ДА → идеальный кейс для агента, можно фоновый (issue → PR)
            └─ НЕТ → агент в IDE, итеративно, с планом
```

### 5.2. Cheat sheet

| Ситуация | Действие |
|----------|----------|
| Новый проект / модуль | Сразу завести контекст-файл: build-команды, инварианты, запреты |
| Типовая задача с тестами | Фоновый агент (issue → PR), ревью как чужого PR |
| Сложная фича | Агент в IDE: план → утвердил → скоуп за скоупом |
| Legacy без тестов | Сначала characterization-тесты, потом агент |
| Агент советует пакет | Проверить на nuget.org: существует + verified publisher |
| AI-тесты подняли coverage | Прогнать Stryker.NET — mutation score покажет цену |
| PR от AI-ревьюера с автофиксом | Новый цикл ревью, не тихий merge |
| Выбор вендора для команды | Data retention, IP indemnity, фильтр public-code совпадений — в чек-лист |

> [!question]- Интервью: как вы контролируете качество кода, написанного AI-агентом?
> Ожидаемые слои ответа: (1) агент работает в цикле с компилятором и тестами — жёсткий build (warnings as errors, анализаторы) даёт автоматические рельсы; (2) diff ревьюится человеком как чужой PR, контракты и миграции — только с approve владельца; (3) метрики честности: mutation testing против vacuous-тестов, lock-файлы против галлюцинированных зависимостей; (4) контекст-файлы (CLAUDE.md/AGENTS.md) кодифицируют конвенции, чтобы агент ошибался реже. Красный флаг в ответе кандидата — «просто внимательно смотрю».

> [!question]- Интервью: чем MCP отличается от function calling конкретного вендора?
> Function calling — механизм одной модели: описания инструментов и формат вызовов у каждого вендора свои. MCP — протокол **между** агентом и инструментом: один сервер работает с любым MCP-совместимым клиентом (Claude Code, Copilot, Cursor, VS Code). Аналогия: function calling — драйвер под конкретную ОС, MCP — USB-стандарт. Детали реализации на C# — [[mcp-csharp]].
